### 1. 数据库引擎
`写事务多用 InnoDB，读多用 MyISAM，临时数据用 Memory。`
**数据库引擎**就是 MySQL 负责存数据和管理索引的组件。常见几种：
- **InnoDB**：支持事务、行锁、多版本控制，适合高并发写操作。
- **MyISAM**：不支持事务，表锁，读多写少，支持全文索引。  
- **Memory**：数据在内存，速度快，但断电丢失，适合缓存或临时表。 
- **Archive**：高压缩，只能插入和查询，适合存历史数据。
    
**总结一句话**：  
写事务多用 InnoDB，读多用 MyISAM，临时数据用 Memory。
### 2. 架构
`客户端发 SQL → 服务器解析优化 → 存储引擎执行存取。`
**数据库架构**主要分三层：
1. **存储层（Storage Engine）**
    - 真正负责存数据、索引、事务等底层操作。   
    - 例子：InnoDB、MyISAM。    
2. **服务器层（Server）**
    - 提供 SQL 解析、优化、权限管理、缓存等功能。 
    - 处理客户端请求，把 SQL 转换成存储引擎操作。   
3. **客户端接口（Client API）** 
    - 提供连接和操作数据库的方法，比如 JDBC、Python MySQL Connector 等。
        
### 3. 不同引擎对索引支持
`选择引擎的时候，看你是否需要事务、外键、聚簇索引或者内存快速访问。`
不同存储引擎对索引的支持不一样：
1. **InnoDB**  
    - 默认支持 **B+ 树索引**（主键索引、普通索引、唯一索引）。      
    - 支持 **聚簇索引**（表数据按主键顺序存储，主键索引就是数据）。      
    - 支持 **外键约束**。       
2. **MyISAM** 
    - 支持 **B+ 树索引**，但是不支持聚簇索引。     
    - 不支持外键。    
3. **Memory（HEAP）**
    - 数据存在内存，支持 **HASH 索引** 和 B+ 树索引。    
    - 适合快速查找，但断电就丢数据。

### 4. InnoDB 与 MyISAM 区别
`InnoDB适合事务型、并发写多的场景；MyISAM适合读多写少、对事务要求不高的场景。`

|特性|InnoDB|MyISAM|
|---|---|---|
|事务|支持（ACID）|不支持|
|锁机制|行级锁|表级锁|
|外键|支持|不支持|
|索引|聚簇索引（主键）|非聚簇索引|
|数据安全|支持崩溃恢复|不支持崩溃恢复|
|存储位置|数据+索引存表空间|数据+索引存文件|
|性能|写入稍慢，读写并发好|写入快，读多写少适合|

### 5. 隔离级别
`MySQL 默认 Repeatable Read，并结合 MVCC 解决了幻读问题，所以实际效果比标准 SQL 定义更
`强。`
MySQL 的事务隔离级别一共 4 种（从低到高）：
1. **读未提交（Read Uncommitted）**
    - 事务可以读到其他事务未提交的数据。      
    - 可能出现：脏读、不可重复读、幻读。     
2. **读已提交（Read Committed）**  
    - 只能读到其他事务已提交的数据。       
    - 避免了脏读，但仍可能出现不可重复读、幻读。    
    - Oracle 默认级别。
3. **可重复读（Repeatable Read）**
    - 同一事务中多次读取结果一致。
    - 避免了脏读、不可重复读，但可能有幻读。
    - InnoDB 通过 **MVCC + Next-Key Lock** 避免幻读。
    - MySQL 默认级别。   
4. **串行化（Serializable）**
    - 强制事务串行执行，读写都会加锁。
    - 完全避免脏读、不可重复读、幻读，但性能最差。
### 6. 最左前缀原则
**概念**  
MySQL 在使用联合索引时，查询条件必须从索引的最左边开始并且连续，否则无法利用到该索引。
**例子**  
假设有联合索引 `(a, b, c)`
- `WHERE a=1` ✅ 用到索引
- `WHERE a=1 AND b=2` ✅ 用到索引  
- `WHERE a=1 AND b=2 AND c=3` ✅ 用到索引 
- `WHERE b=2` ❌ 不能用到索引（因为没从 a 开始）    
- `WHERE a=1 AND c=3` ✅ 只能用到 `a` 部分索引，`c` 不行（中间 b 断了） 
**口诀**  
用到联合索引时，要满足“最左连续匹配”，从最左字段开始，不要跳过。

### 7. MySQL 集群并发方式
`**读写分离、分库分表、分布式集群、多主多活** ——这是 MySQL 集群并发处理的核心手段。`
1. **主从复制（读写分离）**
    - 主库负责写操作，从库负责读操作    
    - 应对读多写少的高并发场景，常配合中间件（如 MyCat、ProxySQL）。    
2. **分库分表（水平/垂直拆分）**
    - 水平拆分：把同一张大表的数据拆分到多个库中，降低单库压力。   
    - 垂直拆分：不同业务的数据分到不同的库，缓解热点表竞争。     
3. **分布式集群（Sharding）**
    - 通过哈希或范围规则把数据路由到不同节点。      
    - 常见于海量并发、高数据量场景（电商、游戏）。    
4. **高可用架构**
    - 使用 MGR（MySQL Group Replication）或 PXC（Percona XtraDB Cluster），保证多主写入和数据强一致。

### 9. MySQL 锁
`·“MySQL 有全局锁，表锁，行锁，读锁，写锁，乐观锁，悲观锁。”`
1. **按粒度分类**
- **全局锁**：锁住整个数据库（`flush tables with read lock`），常用于备份。
- **表级锁**：MyISAM 默认使用，开销小但并发低。   
- **行级锁**：InnoDB 支持，开销大但并发高。
1. **按功能分类**
- **共享锁（S锁）**：多个事务可同时读，但不能写。
- **排他锁（X锁）**：独占资源，阻塞读写。
1. **InnoDB 特有**
- **间隙锁（Gap Lock）**：锁住记录之间的间隙，防止幻读。
- **临键锁（Next-Key Lock）**：记录锁 + 间隙锁组合，保证可重复读。
    
1. **乐观锁 vs 悲观锁**
- **悲观锁**：直接上锁，确保别人不能改，适合高冲突场景。
- **乐观锁**：不加锁，通过版本号或时间戳校验，适合低冲突场景。
    
### 10. delete 与 truncate 区别
`delete 是逐行删，可回滚；truncate 是直接清表，快但不可回滚。`
- **delete**：逐行删除，可带 `where` 条件，产生日志，速度慢，可回滚。
- **truncate**：清空整表，不记录逐行日志，速度快，不能回滚，重置自增主键。

### 11. MySQL 索引（B+ 树）
`B+ 树索引 = 多路平衡查找树，数据都在叶子，支持高效范围查询`
- MySQL 的 **InnoDB 索引**主要用 **B+ 树**实现。
- **B+ 树特点**：
    1. 所有数据都存放在叶子节点，叶子节点之间有链表，便于范围查询。    
    2. 非叶子节点只存储索引键，不存储数据，层高更低，查询更快。    
    3. 适合磁盘存储，减少 I/O 次数。

### 12. B 树与 B+ 树区别
**B 树 vs B+ 树**
- **数据存储位置**： 
    - B 树：数据可以存在所有节点（叶子和非叶子）。      
    - B+ 树：数据只存在叶子节点，非叶子节点只存索引。      
- **范围查询**：
    - B 树：需要在不同节点间跳转，效率低。      
    - B+ 树：叶子节点有链表，范围查询效率高。
- **树高度**：
    - B 树：数据分散，树更高，I/O 更多。    
    - B+ 树：索引更紧凑，树更矮，I/O 更少。
        

👉 **总结**：B 树适合单点查询，B+ 树更适合数据库，支持高效范围查询。

### 13. B+ 树高度计算与容量
**B+ 树高度计算与容量**
- **节点容量**：一个节点大小通常 = 一页（16KB）。 
    - 每个索引项 ≈ 16B（主键 + 指针）。    
    - 所以一个页能存 **16KB / 16B ≈ 1000 条索引**。    
- **高度计算**：
    - 高度 = `log_{每层分支数}(总记录数)`。   
    - 例如：1千万条数据，分支数 1000，`log1000(1000万) ≈ 3`。    
    - 即树高大约 3~4 层。    
- **结论**：  
    B+ 树非常矮，千万级数据也只需 3~4 次磁盘 I/O 就能查到。
### 14. ACID 实现
`原子性，一致性，隔离性，持久性`
**ACID 在 MySQL 中的实现（简洁面试版）**
1. **Atomicity（原子性）**
    - 每个事务作为一个整体执行，要么全成功，要么全失败。
    - **实现方式**：回滚日志（Undo Log）    
    - 引擎：InnoDB 支持事务，MyISAM 不支持。    
2. **Consistency（一致性）** 
    - 事务执行前后，数据库状态满足所有约束（如主外键、唯一性约束）。      
    - **实现方式**：约束 + 触发器 + 程序逻辑。    
3. **Isolation（隔离性）**
    - 并发事务互不干扰。   
    - **实现方式**：锁机制（行锁、表锁）、MVCC（多版本并发控制）    
    - 隔离级别：Read Uncommitted、Read Committed、Repeatable Read（InnoDB 默认）、Serializable。   
4. **Durability（持久性）**
    - 事务提交后，数据永久保存，即使宕机也不丢失。    
    - **实现方式**：重做日志（Redo Log）、双写缓冲（Buffer + 磁盘刷新）。
总结：
- **InnoDB** 完整支持 ACID。
- **MyISAM** 仅支持部分（没有事务和持久性保证）。

### 16. MySQL 事务
`事务就是一组满足原子操作，acid，隔离级别`
**MySQL 事务（面试精简版）**
1. **定义**  
    事务是一组**原子操作**，要么全部执行成功，要么全部失败回滚。
2. **四大特性（ACID）**
    - **Atomicity（原子性）**：事务操作不可分割
    - **Consistency（一致性）**：事务前后数据保持一致   
    - **Isolation（隔离性）**：并发事务互不干扰    
    - **Durability（持久性）**：事务提交后数据永久保存   
3. **隔离级别**
    - **READ UNCOMMITTED**：读未提交    
    - **READ COMMITTED**：读已提交    
    - **REPEATABLE READ**（MySQL 默认）：可重复读
    - **SERIALIZABLE**：串行化   
4. **常用操作**
    `START TRANSACTION; -- 开始事务 COMMIT;           -- 提交事务 ROLLBACK;         -- 回滚事务`
    

简单记：**事务 = 一组操作 + ACID 保证数据可靠 + 隔离级别控制并发**。
### 17. MVCC
`MVCC（多版本并发控制）是数据库中用于实现事务隔离的一种机制，主要用于解决并发读写时的冲突问题。它的核心思想是为每个事务生成数据的一个版本快照，允许多个事务并行操作而不会互相阻塞。`
具体来说：
1. **工作原理**：当事务读取数据时，MVCC会提供一个数据的历史版本（快照），而不是直接访问最新数据。这样，读操作不会被写操作阻塞，实现了读写并发。
2. **关键技术**：
    - **版本号**：每行数据记录版本信息（如事务ID或时间戳），用于区分不同版本。
    - **快照隔离**：读事务根据隔离级别（如读已提交或可重复读）看到一致的数据快照。
    - **垃圾回收**：过期的版本数据会被清理以释放空间。
3. **优势**：
    - 提高并发性能，读写互不阻塞。
    - 支持高隔离级别（如可重复读），避免脏读、不可重复读等问题。
4. **应用场景**：MVCC广泛用于数据库如MySQL（InnoDB）、PostgreSQL等。例如，InnoDB通过Undo Log存储旧版本数据来实现MVCC。
### 18. 锁类型及场景
`锁是用于管理并发访问的机制，确保数据一致性和事务隔离。`根据使用场景和特性，锁可以分为以下几种类型及典型场景：

1. **共享锁（Shared Lock, S锁）**
    - **特点**：允许多个事务同时读取同一资源，但禁止写入。常用于读操作。
    - **场景**：在数据库（如MySQL）中，事务执行SELECT时获取共享锁，确保读数据时不被修改。例如，多个用户查询同一张表的余额数据。
2. **排他锁（Exclusive Lock, X锁）**
    - **特点**：只允许一个事务对资源进行读写操作，其他事务无法读写该资源。常用于写操作。
    - **场景**：数据库中执行UPDATE、INSERT或DELETE时，事务获取排他锁。例如，更新用户账户余额时防止并发修改。
3. **行锁（Row Lock）**
    - **特点**：锁的粒度是单行数据，适合高并发场景，减少锁冲突。
    - **场景**：MySQL InnoDB引擎中，更新表中特定行（如UPDATE WHERE id=1）时使用行锁，适合高并发事务操作。
4. **表锁（Table Lock）**
    - **特点**：锁定整个表，适合低并发或批量操作，粒度较大。
    - **场景**：MySQL MyISAM引擎或执行DDL操作（如ALTER TABLE）时使用表锁，适合批量数据导入。
5. **意向锁（Intention Lock）**
    - **特点**：表级锁，用于表明事务对表中行的锁意图（如意向共享锁IS、意向排他锁IX），提高锁兼容性检查效率。
    - **场景**：InnoDB中，事务在获取行锁前会先获取表级意向锁，协调行锁与表锁。
6. **乐观锁（Optimistic Lock）**
    - **特点**：假设冲突少，先操作数据，提交时检查是否被修改（如通过版本号或时间戳）。
    - **场景**：高读低写场景，如电商库存扣减，配合版本号字段（version）检查冲突。
7. **悲观锁（Pessimistic Lock）**
    - **特点**：假设冲突多，操作前先加锁（如共享锁或排他锁），确保独占资源。
    - **场景**：高并发写场景，如金融系统转账操作，使用SELECT ... FOR UPDATE加悲观锁。
8. **间隙锁（Gap Lock）与记录锁（Record Lock）**
    - **特点**：间隙锁锁定索引间范围，防止幻读；记录锁锁定单条索引记录。
    - **场景**：InnoDB的可重复读隔离级别下，防止插入新记录导致幻读，如范围查询（SELECT WHERE id BETWEEN 10 AND 20 FOR UPDATE）。

**总结**：锁类型根据粒度（行锁、表锁）、用途（共享、排他）和策略（乐观、悲观）分类，不同场景选择合适的锁能平衡并发性能和数据一致性。例如，InnoDB的MVCC结合行锁和间隙锁支持高并发，乐观锁适合读多写少的场景。
### 19. 死锁成因与例子
死锁是指多个事务或进程因互相持有对方所需的资源并等待对方释放，导致所有事务都无法继续执行的状态。死锁是并发控制中的常见问题，尤其在数据库或多线程编程中。

**死锁的成因（四个必要条件）**：

1. **互斥条件**：资源只能被一个事务/进程独占（如数据库中的排他锁）。
2. **持有并等待**：事务/进程持有至少一个资源，同时等待其他资源。
3. **不可抢占**：资源只能由持有者主动释放，无法被强行夺取。
4. **循环等待**：多个事务/进程形成一个环路，各自等待对方持有的资源。

 **死锁的例子**： 假设在一个电商系统中，两个事务T1和T2同时处理订单和库存：

- T1：用户A下单，事务先锁住订单表（UPDATE orders SET status='paid' WHERE order_id=100 获取订单100的排他锁），然后尝试更新库存表（UPDATE inventory SET stock=stock-1 WHERE product_id=200 等待产品200的锁）。
- T2：用户B下单，事务先锁住库存表（UPDATE inventory SET stock=stock-1 WHERE product_id=200 获取产品200的排他锁），然后尝试更新订单表（UPDATE orders SET status='paid' WHERE order_id=101 等待订单100的锁）。
- 结果：T1持有订单100锁等待产品200锁，T2持有产品200锁等待订单100锁，形成循环等待，导致死锁。

**场景**：死锁常出现在高并发场景，如电商系统中的订单处理、金融系统的账户转账，或多线程程序竞争共享资源（如Java中线程锁）。
### 20. 事务安全
`事务安全是指数据库事务在并发执行时保证数据一致性和可靠性的能力，通常通过事务的ACID特性来实现。事务是一组操作的原子单位，要么全部成功，要么全部回滚。`

**ACID特性**：

1. **原子性（Atomicity）**：
    - **定义**：事务的所有操作要么全部执行成功，要么全部回滚，不允许部分执行。
    - **保障机制**：通过Undo Log（如MySQL InnoDB）记录事务修改前的状态，若失败则回滚。
    - **场景**：银行转账中，从账户A扣款和向账户B加款必须同时成功或失败。
2. **一致性（Consistency）**：
    - **定义**：事务执行前后，数据库从一个一致状态转换到另一个一致状态，满足约束（如外键、唯一性）。
    - **保障机制**：通过数据库约束、触发器和事务隔离级别保证。
    - **场景**：转账后，账户余额总和保持不变，满足业务规则。
3. **隔离性（Isolation）**：
    - **定义**：事务之间相互隔离，防止并发操作导致数据不一致。
    - **保障机制**：通过锁机制（如行锁、表锁）或MVCC（如InnoDB的快照读）实现不同隔离级别（如读已提交、可重复读）。
    - **场景**：用户A查询余额时，不受用户B同时转账的影响，避免脏读或幻读。
4. **持久性（Durability）**：
    - **定义**：事务提交后，数据修改永久保存，即使系统故障也不会丢失。
    - **保障机制**：通过Redo Log记录已提交事务的修改，系统恢复时重放日志。
    - **场景**：转账提交后，即使数据库崩溃，重启后数据依然有效。

**典型问题与解决方案**：

- **脏读、不可重复读、幻读**：通过设置适当的隔离级别（如可重复读）和MVCC解决。
- **死锁**：通过规范化资源访问顺序或死锁检测（如InnoDB的等待图）避免。

**场景**：事务安全广泛应用于金融系统（如转账）、电商（订单与库存更新）等场景。例如，MySQL InnoDB通过MVCC和日志机制保障高并发下的事务安全。

**总结**：事务安全通过ACID特性确保数据一致性和可靠性，结合锁、MVCC和日志机制应对并发场景，是数据库核心功能之一。
